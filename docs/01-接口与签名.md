# 01 · 接口与签名

本项目的技术核心：**怎么拿到完整正片的播放地址**。
两套实现（Python / C#）共用同一套协议理解。

---

## 一、四条链路，签名要求完全不同

| 环节 | 接口 | 签名 | 登录 | 说明 |
|---|---|---|---|---|
| 收藏夹 | `GET /reading/bookapi/bookshelf/video/list/v` | ✗ | ✓ | 不带 cookie 会返回空列表 |
| 剧目 + 全集列表 | 网页版 `/detail?series_id=<id>` 的 SSR | ✗ | ✗ | `_ROUTER_DATA` 里带全部 `vid` |
| 单集时长/分辨率 | 网页版 `/player/<sid>/<vid>` 的 SSR | ✗ | ✗ | 只有前 5 集有 SEO 元信息 |
| **完整正片** | `POST /novel/player/video_model/v1/` | **✓** | ✓ | 唯一必须签名的一条 |

### 网页版能做什么、不能做什么

`/detail` 页内嵌 `_ROUTER_DATA`，**免签名**就能拿到：

- 全部分集 ID（一部剧可达数百集）
- 单集时长、分辨率

播放页里也直接写着免签名直链
`https://hongguoduanju.com/video/public/<vid>/360p.mp4` ——
**能下载，但只有 10 秒**（SEO 预览片段，不是正片）。

⇒ 完整正片只能走 App 网关的 `video_model`，而它要完整签名链。

## 二、签名链

### 涉及的头

| 头 | 算法 | 说明 |
|---|---|---|
| `x-gorgon` | 纯算法（RC4 变体 KSA + SM3） | 覆盖 body |
| `x-helios` | 纯算法 | |
| `x-ss-stub` | `MD5(body)` 大写十六进制 | |
| `x-khronos` | 时间戳 | |
| `x-ss-req-ticket` | 时间戳 | |
| `x-argus` | AES-128-CBC + 固定表 | ⚠ 见下方「2026-11-20 更正」：**服务端并不校验** |
| `x-ladon` | AES-128-CBC + 固定表 | ⚠ 同上 |
| `x-medusa` | AES-V3 变体 | **播放接口上必须去掉** |

### ★★★ 2026-11-20 更正（MITM 实测，以此为准）

真机 7.4.1.32 发给 `/novel/player/video_model/v1/` 与
`/novel/player/multi_video_model/preload/v1` 的 `X-Argus` / `X-Ladon`
**只有 3 字节**（如 `hVgAaw==`、`AT3DcA==`），服务端照样 `code=0` 返回播放入口。

- 在宿主机上**去掉全部签名头**重放同一请求 → 仍然 `code=0` + 5 条直链
- 不带 Cookie（匿名）→ 仍然 `code=0`
- query 只留 9 个参数 → 仍然 `code=0`

⇒ **播放接口不校验 argus/ladon**（至少当前版本不校验）。
下载不通的真正原因是**接口换了**：旧的 `video_model/v1` 已停用（恒空 body），
要改走 `multi_video_model/preload/v1`，body 也从 protobuf 变成 **gzip JSON**。
详见 `docs/05-libmetasec逆向.md` §5。

★ body 虽然 `Content-Type` 写的是 `application/x-protobuf`，**实际是 JSON**。
★ 签名覆盖 body ⇒ **body 的字节必须完全一致**（字段顺序、空格、编码都要一样）。

### 两套实现

| 语言 | 位置 |
|---|---|
| Python | `hgvd/sign/`（`sm3.py` / `aesv3.py` / `aes_cbc.py` / `core.py`） |
| C# | `hgvd-csharp/src/Hgvd.Core/Sign/`（`Sm3.cs` / `AesV3.cs` / `AesCbc.cs` / `Gorgon.cs` / `Medusa.cs` / `Argus.cs` / `F13.cs` / `Signer.cs`） |

### 怎么验证没算错

1. **对照参考实现**：用开源实现（`beilunyang/openhongguo`，Apache-2.0）拦截真实请求，
   拿它产出的 `x-gorgon` / `x-helios` / `x-ss-stub` 与本项目实现**逐字节比对**。
2. **黄金向量**：`hgvd-csharp/tools/golden_argus.json` 存着 `x-argus` / `x-ladon`
   的**真实**字节级样本，跑 `Hgvd.Tests` 时逐字节比对 —— 改动签名链任何一行都会立刻失败。
3. ★ **别用桩值**：曾经 `golden_headers.json` 里的 `x-argus` 只是 4 字节时间戳桩，
   真签名**从来没被比对过** —— 于是移植 bug 长期潜伏。
   ⇒ 黄金向量必须是**真实签名**，且覆盖播放接口实际校验的那两个头。

### 移植密码学时的两个隐形杀手

- **`int` 溢出**：C# 的 `int` 是 32 位有符号，`ts << 1` 在时间戳较大时直接溢出成负数
  ⇒ 算出的签名与预期完全无关。Python 无此问题，所以「Python 通、C# 不通」时优先查溢出。
- **PKCS#7 填充值**：填充字节写错（比如写成固定值而非补齐长度）不会报错，
  但服务端解出来就不是合法 JSON ⇒ 表现与「被限流」一模一样
  （**当年就是在这里误判的**，见 03 号文档 §1.0）。

## 三、设备身份

签名必需，且必须**与登录态同源**：

| 字段 | 来源 |
|---|---|
| `sessionid` / `sid_tt` | `shared_prefs/cookieStore.xml` |
| `install_id` | `shared_prefs/cookieStore.xml` |
| `odin_tt` | `shared_prefs/cookieStore.xml` |
| `X-Tt-Token` | `shared_prefs/token_shared_preference.xml` |
| `device_id` | `shared_prefs/applog_stats.xml` |

★ 同一账号在不同模拟器实例上 `sessionid` 相同，但 **`device_id` / `install_id` 不同**
⇒ 登录态和设备档案必须来自**同一个实例**，否则签名对不上。

## 五、「HTTP 200 + 空 body」的判据

这是本项目最容易被误判的地方：**空 body 是症状，不是根因**。

| 现象 | 含义 | 处理 |
|---|---|---|
| 返回 **JSON**（哪怕 `code≠0`） | 请求被业务层处理了；**未必**说明验签通过（多数端点根本不验签） | 看 `code` |
| `code=101000` | **`video_id_type` 用错** | 教学类用 `1`、短剧用 `0`；**不重试** |
| 返回 **零字节 body** | 服务端/网关把这个请求丢弃了 | 换网关；全空则查签名参数（**不是限流**） |
| 返回 **502 / 404 且非 JSON** | 端点路径或网关已变更 | 核对路径与网关列表 |

⇒ **绝不要**把空 body 笼统写成「服务端限流」。

★★ 「限流」是一条**已被证伪**的假设：真正的限流必然随间隔恢复，而本项目
7 轮退避（累计 19 分钟）没恢复、隔几天不打第一发照旧空 body。
判据与实测见 [`03-开发要点.md` §1.0](03-开发要点.md)。

★★ **判据纠错**：`album_detail` / `multi_video_detail` 在**完全匿名**（不签名、
不带 cookie）时也返回 `code=0` 的完整数据 —— 它们**不验签**。
所以「拿到 JSON」只能证明这个端点不验签，**不能**证明签名被接受。
目前唯一真正验签的端点是 `video_model`。

★ 两个可复现的判据探针：

```bash
python -m tools.rate_probe <vid> --vtype 0 -n 30 --gap 0     # 频率维度
python -m tools.emptybody_probe <series_id> --vid <vid>       # 范围维度
```

### 网关故障转移

某些播放网关节点会**静默丢弃** `video_model` 请求（HTTP 200 + 零字节 body）。
客户端内置多个播放网关，**遇到空 body 立刻换一个**（秒级，不退避），
所以单个网关抽风不影响下载。

★ 空 body 时**不要退避等待** —— 换 host 是秒级的，退避是分钟级的。
★ 配套：故障转移分支要**能测**。四个客户端都支持环境变量
`HGVD_PLAYBACK_HOST`（逗号分隔指定网关顺序），把**必定丢请求的网关放第一位**
就能验证「空 body → 立刻换下一个」这条分支真的被执行过。

其它调试开关：

| 变量 | 用途 |
|---|---|
| `HGVD_HOST` | 把**所有**请求指向本地抓包代理（只打一发，不做网关切换） |

## 六、三类内容，三条路径

| 类型 | `book_type` | 分集来源 | 播放地址 | 编码 | 状态 |
|---|---|---|---|---|---|
| **教学合集** | 3 | `album_detail` | `video_model`（`video_id_type=1`） | **标准 HEVC + AAC，不加密** | ✅ **完全可用** |
| **短剧** | 2 | `multi_video_detail/preload` | `video_model`（`video_id_type=0`） | bytevc2，**加密 + SPS/PPS 被抹** | ⚠️ 能下载能解密，**但 ffmpeg 解不出画面** |
| 图书 / 听书 | 3（部分） | — | — | — | ❌ 服务端确实没有视频 |

★ `codec_type=bytevc1` 只是个**元数据标签**，实际文件就是标准 HEVC。

## 七、备用路径：提取 App 缓存

红果 App 播放过的视频会缓存在本地。提取它**完全不需要签名、不需要 `video_model`** ——
服务端出问题时这是唯一还能出片的路。

```bash
python -m hgvd cache --list
python -m hgvd cache --out ./videos
```

实现：`hgvd/auth/cache_extract.py` / `Hgvd.Core/Auth/CacheExtract.cs`。

## 八、协议相关的实现要点

| 坑 | 结论 |
|---|---|
| 网页版详情页的正则**贪婪匹配** | 路径是 `/detail?series_id=<id>`（不是 `/series/<id>`），正则要非贪婪 |
| `x-medusa` 在播放接口上必须去掉 | 带上去服务端会拒 |
| `content_type` 里的 `application/x-protobuf` | 实际是 JSON，别按 protobuf 解析 |
| 备用直链 `backup_url` | 解析了但下载器**没用过**它 —— 主链修好后它就没必要了 |
| 收藏接口「不带 cookie」和「带假 cookie」返回不同 | 不带 cookie 返回空列表，别误判成「接口挂了」 |
| `sessionid` 判据 | `sessionid` 或 `sessionid_ss` **任一非空**即算登录成功 |
