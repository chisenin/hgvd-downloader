# 10 · 红果 / 兴趣岛两源对照与内核统一

> 2026-11-22。回答一个问题：**两个内容源能不能只剩一个核心？**
> 结论：**协议层不能，下载/队列层可以，而且应该。**
> 目标形态是一套下载内核 + 两个「源适配器」。
> 本版已落地：P1（状态词 / 去重 / 混合调度 / 重扫）、P2（统一清单 `downloads.json` /
> 兴趣岛直链复用单文件引擎 / 暂停抽象）、P3（两源共用顶层工位池与暂停闸门；
> 源内状态机仍各管各的，理由见第五节）。

---

## 一、判定标准

只看一条：**差异是「数据形状不同」还是「业务步骤不同」**。

- 数据形状不同（单文件 vs HLS、mp4 vs m3u8、字节进度 vs 时长进度）
  → 可以做成同一个核心里的两个引擎分支，对外呈现仍是一张表。
- 业务步骤不同（签名请求 vs Cookie 请求、CENC 解包 vs 明文孪生、空 body 熔断）
  → **必须留在各自的适配器里**，硬合并会把一侧的判据带到另一侧，制造假故障。

## 二、分层对照

| 层 | 红果 | 兴趣岛 | 判定 |
|---|---|---|---|
| 协议 / 鉴权 | 客户端签名链 + 设备身份；Cookie 存 `cookie.json` | `qianliao` 网关 + `userId`/`rsessionId`；Cookie 存 `xqd\cookie.txt` | **不合并**（凭据与请求形状不同，只共用 MuMu 取数） |
| 播放地址 | 每集 `playback`；入清单预热 + 15s 单集超时 + 空 body 熔断 | 每节 `getCoursePlayUrl`，现场解析不缓存 | **不合并**（熔断只对红果成立） |
| 媒体形态 | 单文件 MP4，可能有 CENC 内容密钥 | HLS：多码率 / 加密孪生 / 直链音频 | **分引擎**（见第五节 `PlayRef.Kind`） |
| 单文件下载 | `Core.Engine.Downloader`：Range 续传、`.part` 原子改名、备用直链、ffprobe 校验 | 旧 `DirectDownloader`：随机临时文件、无续传、无备用直链 | ✅ **已合并**（P2：兴趣岛直链复用 Core 引擎，网络层仍注入自己的 `HttpClient`） |
| 分片下载 | 无 | 12 片等距抽样估总字节 + 12 路并发 + `%05d_` 续传 | 兴趣岛专用，保留 |
| 封装 | 无（CENC 解密后 `-c copy`） | 字节拼 `all.ts` → ffmpeg | 兴趣岛专用，保留 |
| 队列 / 状态机 | 调度在 `MainWindow`，清单落 `queue.json`（只存成员） | `XqdQueue`，清单落 `xqd\jobs.json`（含状态） | 清单已合并（P2）；顶层工位池已共用（P3），源内状态机仍两段 |
| 状态词 | 引擎阶段名直接写进界面（「下载 / 解密 / 校验」） | `XqdState`（「下载中 / 封装中 / 校验中」） | ✅ **已合并**（`JobState`，本版） |
| 「已存在」判定 | 各自内联 `max(3s, 2%)` | `XqdDedupe` 的 `max(1s, 0.5%)` | ✅ **已合并入口**（`ExistingArtifact`，容差按源） |
| 重扫（按磁盘重判） | 记账命中秒跳 + 无记账 4 路并行 ffprobe | 串行 ffprobe（在锁内） | ✅ **已吸收**（兴趣岛改异步 + 4 路并行） |
| 进度模型 | 字节（`Done/Total`） | 字节 + 内容时长（`dur`/`byte`） | 共用一行展示；底层单位保留（P3 不再强并） |
| 暂停 | `PauseGate`（分块之间等） | `XqdControl.Paused`（分片之间等） | ✅ **真正共用一个闸门**（P3：`XqdControl` 包同一个 `PauseGate`） |
| 预取 | 下载游标前 10 集预解析 | 无 | 未吸收（兴趣岛解析本身很快，见第四节） |
| 预检 / 记账 | `progress.json` 记账 + 预检表 | 无记账，靠统一清单状态 + 重扫 | 未吸收（源内状态机保持独立） |
| 空 body 熔断 | 有（只对红果） | 无 | 不合并 |
| 界面 | 右栏、筛选、右键、日志、底栏、目录 | 同左 | 已共用；剩余差异见第四节 |

## 三、本版已统一（2026-11-22）

### 3.1 状态词只有一个定义处

- 新增 `Hgvd.Core/Download/JobState.cs`；`Hgvd.Xqd.XqdState` 改为**转发**，不再自己定义。
- 红果引擎 `Engine/Downloader` 不再上报「下载 / 解密 / 校验」这种阶段名，直接上报
  `下载中 / 解密中 / 校验中`；`PhaseWord` 仍保留给兴趣岛引擎。
- 新增 `解密中`（红果 CENC 解包阶段），同时进「下载中」筛选与状态胶囊配色。

**修掉的真实缺陷**：红果行下载时状态是「下载」，而 5 档筛选的「下载中」只认
「排队中/解析中/下载中/封装中/校验中」—— 红果行在「下载中」筛选下会**消失**；
`IsRunning` 也判不到它（暂停/收尾统计会漏）。现在两源同一套词，筛选、配色、统计一致。

### 3.2 「已存在」判定只有一个入口

- 新增 `Hgvd.Core/Download/ExistingArtifact.cs`：`≥1MiB` + 预期时长 vs ffprobe。
- 红果预检、红果单集兜底、兴趣岛 `Rescan` 三处全部改走它。
- 容差**按源标定**，不强行同数值：
  - 红果 `max(3s, 2%)`：预期时长来自播放接口标称值，实测常有 1~2 秒差；
  - 兴趣岛 `max(1s, 0.5%)`：预期时长是 EXTINF 逐片精确累加。
- 统一的是**判定结构**（体积门槛 + 时长比对 + 读不出时回退体积），不是把 0.5% 套到红果上。

### 3.3 混合清单同一批开跑

- 以前：红果整批跑完，才轮到兴趣岛。混合选中时，兴趣岛的行一直停在「待下载」，
  看起来像没被点中。
- 现在：两边同时开始，共用一个「下载 / 暂停 / 继续」按钮、一个取消令牌、一个日志。
- 并发上限：红果 2 个网络工位；**混合时**兴趣岛课间并发降到 1
  （1 课 × 12 分片 + 2 条红果流），不高于兴趣岛自己「2 课 × 12 片」的峰值。
  纯兴趣岛批次仍是 2 课并发。

### 3.4 兴趣岛重扫不再卡界面

- `RescanAsync`：先做无 IO 的判定，需要 ffprobe 的 4 路并行，最后在锁内一次性应用。
- 100 条已存在清单的判定从 ~4.5s 降到 ~1s，且混合下载开始时界面不冻结。
- `Rescan()` 保留为同步外壳（回归/无 UI 上下文），内部仍走异步实现。

### 3.5 「重新下载（清缓存）」语义对齐

- 两源都只清**临时文件 / 分片**，不动成品；成品仍在时下次按「已存在」跳过。
- 要真正重下，先删成品。日志文案现在两源一致，不再出现
  「红果说会跳过、兴趣岛却真的覆盖重下」这种同名不同行为。

## 四、仍然不一致的地方（有意保留 / 待改）

| 项 | 现状 | 判断 |
|---|---|---|
| 进度单位 | 红果按字节；兴趣岛按内容时长（直链音频才按字节） | **保留**。HLS 只有时长精确，字节是抽样估算；两者都映射到同一行的百分比/大小/剩余时间 |
| 分片并发 | 兴趣岛课内 12 路；红果单流 | **保留**。这是两种媒体的最优解，不是体验差异 |
| 解析停顿 | 红果有 10 集预取窗口；兴趣岛每节开下前现场解析 | **暂不吸收**。兴趣岛解析通常 <1s，预取收益低且会多打网关；若实测变慢再按红果窗口做 |
| 下载前「预计大小」 | 红果解析后即可显示 `≈`；兴趣岛要等抽样 | **未做**（后续：加入清单时先显示时长，抽到总字节后补 `≈`） |
| 持久化 | `queue.json`（成员）/ `xqd\jobs.json`（含状态）两套 | ✅ **已合并**（P2：一个 `downloads.json`、两源 section、旧文件一次性迁移） |
| 直链续传 | 兴趣岛直链断点重来 | ✅ **已吸收**（P2：复用 Core 单文件引擎，Range 续传 + `.part`） |
| 「已暂停」行状态 | 两源都只在底栏/按钮显示，不给行打「已暂停」 | **保留**（暂停是全局态，逐行打标反而会掩盖真实阶段） |
| 质量档位 | 红果按分辨率后缀；兴趣岛按短边 | **保留**（选流逻辑不同）；下拉框按源切换已经统一 |

## 五、目标架构：一个下载核心 + 两个源适配器

```
ISourceAdapter                       ← 差异都关在这里
├── HongguoAdapter                   签名请求 / 预热 / 熔断 / CENC 密钥
└── XiqudaoAdapter                   Cookie / 课表 / getCoursePlayUrl
      Resolve(job, ct) -> PlayRef { Kind: Direct | Hls, Url, BackupUrl, Key, Headers, ExpectDuration }

DownloadQueueCore                    ✅ P3（只统管资源，不统管源语义）
├── 顶层工位池：红果每集 1 格、兴趣岛每课 1 格；混合 3 格，纯源 2 格
├── 暂停闸门：两源同一个 PauseGate（按钮只改一处状态）✅
├── DownloadManifestRecord（source/group/seq/title/outPath/expectDuration/state，两源共用）✅
├── 持久化：一个 downloads.json ✅
├── ExistingArtifact / Naming / History ✅ 已抽出
├── FileEngine（Direct：单文件 + Range 续传 + 备用直链）✅ 两源共用
└── HlsEngine（Hls：抽样 / 分片 / 封装；仅兴趣岛会返回 Hls）

状态机                                ← 仍由两个源适配器各自管
├── 红果：MainWindow 的预检 / 熔断 / 进度回调
└── 兴趣岛：XqdQueue 的课表解析 / HLS 分片 / 封装

UI                                   ← 一张表
└── 清单 / 筛选 / 右键 / 历史 / 日志 / 底栏 / 目录
```

`DownloadManifestRecord` 需要的字段已经能从两侧现有模型一一映射：

| DownloadManifestRecord | 红果 | 兴趣岛 |
|---|---|---|
| `Source` | 固定 `Hongguo` | 固定 `Xiqudao` |
| `Group` | 剧名（`SeriesTitle`） | 营名（`Camp`） |
| `Seq` | 集号 `Index` | 课序号 `Seq` |
| `ExpectDuration` | `Episode.Duration` | `Lesson.Duration` / 链接里的时长 |
| `Resolve` | `ResolveFullUrlAsync` | `QianliaoPlatform.ResolveJobAsync` |
| `OutPath` | `BuildOutPath` | `XqdQueue.OutPathFor` |

| 阶段 | 内容 | 状态 |
|---|---|---|
| **P1（2026-11-22）** | 状态词、去重入口、混合调度、异步重扫、重下语义 | ✅ 已回归 |
| **P2（2026-11-22）** | 统一清单 `downloads.json`（两源 section + 旧文件迁移）、兴趣岛直链改用 Core 单文件引擎、`IPauseToken` 抽象、Range 被忽略时的截断保护 | ✅ 已回归（+14 项清单测试） |

### P2 实现要点（2026-11-22）

- `downloads.json` 结构：`{ Version, HongguoImported, XiqudaoImported, Groups[] }`；
  每个 group 带 `Source`，每条记录带两源重建所需的全部字段。
- 迁移：首次加载各自读旧 `queue.json` / `xqd\jobs.json`，写进统一清单后打 imported 标记；
  **旧文件不删**，但打标记后不再读（避免清空清单被旧文件「复活」）。
- 先保存后加载也不丢：`Store` 不提前打 imported，迁移按「GroupId + 标题」合并、
  按记录 `Id` 补缺，现有行优先；只有用户显式清空（`Clear`）才压掉迁移。
- 两源各写自己的 section：兴趣岛保存不会冲掉红果字段，反之亦然。
- 兴趣岛直链：`DirectDownloader` 不再自己写 HTTP 循环，改调 `Core.Engine.Downloader`；
  临时名固定为 `<成品>.download`，中断后 `.part` 可续传；网络层仍用 `XqdNet` 的客户端（`DownloadRequest.Client`）。
- 暂停：`PauseGate` 与 `XqdControl` 都实现 `IPauseToken`，引擎只认这一个接口。
- 顺手修的通用缺陷：服务器不认 `Range` 却回 200 时，旧 `.part` 会被追加成双份成品；
  现在检测到 200 + 已有 `.part` 会先截断再写。

### P3 实现要点（2026-11-22）

- 新增 `Hgvd.Core/Download/DownloadQueueCore.cs`：一个 `SemaphoreSlim` 工位池 + 一个 `PauseGate`；
  租约 `SlotLease` 重复 Dispose 不会多归还，排队可取消。
- `MainWindow.DownloadRowsAsync` 每批只建一个池：
  - 纯红果 / 纯兴趣岛 2 格；混合 3 格（红果 2 + 兴趣岛 1）。
  - 红果另有一道自己的 2 格闸门：否则红果派发循环会先把 3 格全拿走，
    混合批次又会退化成「先红果、兴趣岛干等」。
- `XqdQueue.RunAsync` 新增可选 `DownloadQueueCore queue` 与 `IPauseToken pause`：
  每节课先拿本队列的课间闸门（混合 1 / 纯兴趣岛 2），再向共用池拿 1 格；
  课内 12 路分片仍在课内自己管，不占额外顶层工位。
- 暂停真正共用：`XqdControl` 可包一个共享 `PauseGate`，`Paused` 读写都落到同一闸门；
  `RunAsync` 把 `_control` 传给直链 / HLS 引擎，两源在同一个按钮下冻结与恢复。
- **没有把两套状态机并成一个**：红果的「集」是单文件 + 预检记账 + 空 body 熔断，
  兴趣岛的「课」是 HLS 多分片 + 课表解析 + 加密孪生；状态词相同，
  但失败语义和资源单位不同。硬并会得到一个到处 `if (source)` 的通用状态机，
  代码不会更少，回归面却更大。P3 只收口「谁能开始、最多几格、暂停算谁的」，
  源内状态仍由适配器自己管。

## 六、不要合并的红线

- 红果签名链、设备身份、CENC 内容密钥解包 —— 只属于红果适配器。
- HLS 的 12 片抽样、`%05d_` 分片名、字节拼接、加密清单找明文孪生 —— 只属于 HLS 引擎。
- 两套 Cookie 的读取来源与域名匹配 —— 各读各的 App，只共用 MuMu 执行层。
- 「空 body → 熔断」只对红果播放接口成立，**不能**推广到兴趣岛。
- 抓包、重放、探针、样本一律不进公开文档（见 [`docs/README.md`](README.md) 维护约定）。
