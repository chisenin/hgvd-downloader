# 02 · 版本与维护范围

---

## 一、只维护两套实现

| 角色 | 实现 | 位置 | 形态 |
|---|---|---|---|
| **发行版**（日常使用） | **C# + Avalonia 11** | `hgvd-avalonia/` | **自包含目录版 + zip**（约 54 MB，.NET 运行时与 ffmpeg/ffprobe 全部内置，目标机零安装）；另附单文件 exe（约 58 MB）备用 |
| **想法验证**（改逻辑用） | **Python** | `hgvd/` | 命令行 + 本地网页界面，依赖极少 |
| 共享核心 | C# `Hgvd.Core` | `hgvd-csharp/src/Hgvd.Core/` | 签名链 / 下载器 / 配置目录 / 设备身份 |
| 兴趣岛内核 | C# `Hgvd.Xqd` | `hgvd-csharp/src/Hgvd.Xqd/` | 取授权（**雷电 adb 优先，MuMu 兜底**）/ 营与课表自动发现 / HLS 分片下载 / ffmpeg 合成（**不含** ADB 界面自动化） |
| 离线回归 | C# `Hgvd.Tests` | `hgvd-csharp/src/Hgvd.Tests/` | 205 项断言 / 13 组 |

> ★ 两套实现**共用同一套核心**与协议理解，登录态 / 设备档案 / 下载历史可以直接互换。
> 协议细节见 [`01-接口与请求.md`](01-接口与请求.md)。

**为什么这样分工**：Python 版改逻辑快（改完跑一遍就知道对不对），
适合验证接口与算法；Avalonia 版做成交付形态，适合日常使用。
核心修复只改一处（`Hgvd.Core`），两边同时受益。

## 二、构建

### Python 版

```bash
pip install -r requirements.txt
python -m hgvd --help
```

### C# + Avalonia 发行版

```bash
cd hgvd-avalonia
./build.sh            # 或 Windows 下 build.cmd
```

产物（**本地只出目录版**；GitHub Release 另有 zip + 单文件）：

| 形态 | 路径 | 体积 | 谁产出 |
|---|---|---|---|
| **目录版**（本地唯一形态） | `hgvd-avalonia/pkg/hgvd-downloader-vX.Y.Z/` | 约 77 MB / 99 个文件（含 LICENSE.txt / NOTICE.txt） | 本地 `build.cmd` / `build.sh` |
| 目录版压缩包 | `hgvd-avalonia/dist/hgvd-downloader-vX.Y.Z-win-x64.zip` | 约 54 MB | **仅 CI**（`release.yml`） |
| 单文件（备用） | `hgvd-avalonia/dist/hgvd-downloader-vX.Y.Z.exe` | 约 58 MB | **仅 CI**（`release.yml`） |

> ★ **2026-11-21 用户拍板：本地不再打 zip、不再出单文件 exe** —— 自用直接跑
> `pkg\` 里的 exe 即可。**GitHub Release 的产物形态不变**（远端给公众下载仍是
> zip + 单文件，由 CI 产出，与本地构建脚本无关）。
> 为什么主推目录版：启动更快、ffmpeg 可替换、出问题能直接看目录里有什么；
> 单文件把 ffmpeg 内嵌后是"假单文件"（首次运行仍要解压到 `%LOCALAPPDATA%`），
> 而且"exe 解出 exe"容易触发杀软启发式。选型讨论见 `03-开发要点.md` §3.6。

> ★ `v1.4.0` 是**合并兴趣岛后的版本**（`v1.3.0` 标签指向合并前的 `6cbe4c2`，只有红果）。
> 版本号统一用 `python tools/bump_version.py <x.y.z>` 改，别手工改三处。

构建分三步，发版再加一步验证：

| 步 | 做什么 |
|---|---|
| 1 | `prepare-ffmpeg.ps1` —— 从 npmmirror 取 `@ffmpeg-installer/win32-x64` 与 `@ffprobe-installer/win32-x64`，解出 exe 压成 `..\.cache\ffmpeg\*.exe.gz`（已存在则跳过） |
| 2 | `dotnet restore -p:Configuration=Release --configfile NuGet.config -r win-x64`（★ 这个 `-p:Configuration=Release` 不能省，否则 ILLink 拉不到、裁剪静默失效，见 `03-开发要点.md` §3.6） |
| 3 | `dotnet publish ... -p:PublishSingleFile=false -o pkg\<APP>\` —— 目录版（`.exe.gz` 作为 `EmbeddedResource` 嵌入主程序集） |
| 4 | **发版必做**：`build.cmd verify` / `build.sh verify` —— 构建后再跑 `--uitest`（界面自检）+ `--tlsprobe`（证书链）+ `--dlprobe`（下载链路），**验的是目录版**。`tools/publish_release.sh` 会检查这三份日志是否在 24 小时内且通过，不过就拒绝打标签。见 `03-开发要点.md` §6.1 |

发布配置（`Directory.Build.props` + `Hgvd.Avalonia.csproj`）：
自包含 / 单文件 / 压缩 / `PublishTrimmed` + `TrimMode=partial`，
并保根 `Avalonia.*` 与两个自有程序集（反射绑定的前提，见 `03-开发要点.md` §3.6）。

运行时由 `FfmpegRuntime.Ensure()` 在界面起来之前把内置资源流式解压到
`%LOCALAPPDATA%\hgvd-downloader\runtime\ffmpeg-<程序集版本>\`，路径交给
`Hgvd.Core.ToolPaths`；目录已存在就直接复用，所以只有首次启动慢几秒。
`Hgvd.Core` 里所有 `ProcessStartInfo("ffmpeg"/"ffprobe")` 都走 `ToolPaths`，找不到内置的就回退 PATH。

> ★ `Hgvd.Core` 在 `hgvd-csharp/` 下，而 `NuGet.config` 在 `hgvd-avalonia/` 下 ——
> NuGet 配置是**按项目目录向上查找**的，所以发布前必须显式
> `dotnet restore --configfile NuGet.config -r win-x64`（构建脚本已经带上了）。
> 少了这一步会报 `NU1100：无法解析 Microsoft.NETCore.App.Runtime.win-x64`。

## 三、离线回归

两套回归都**不发网络请求**，几秒出结果，用来挡住签名链 / 请求头 / 播放协议 / 界面回归的破坏。

```bash
# Python：134 项（I 组 17 项守 preload 协议与「不校验签名头」的结论；
#         J 组守抓流白名单口径；含「收藏夹外的教学合集不入队」「无旁路开关」等新护栏）
python -m tests.run

# C#：205 项断言 / 13 个测试组（签名黄金向量 + 完整请求头 + x-argus/x-ladon 字节级
#         + 发行版界面 + 命名规则 + MuMu 安装位置发现 + adb 探测 + 设备档案 + DRM
#         + 兴趣岛内核：链接解析/清单/命名/队列/课表任务/Cookie 解析
#         + 清单/历史/去重：QueueStore/HistoryStore/XqdDedupe/筛选/剩余时间/PauseGate
#         + 抓流常驻循环状态机 + 抓流白名单准入：白名单命中是唯一准入条件）
dotnet restore hgvd-csharp/src/Hgvd.Tests/Hgvd.Tests.csproj --configfile .github/nuget.ci.config
dotnet build   hgvd-csharp/src/Hgvd.Tests/Hgvd.Tests.csproj -c Debug --no-restore
./hgvd-csharp/src/Hgvd.Tests/bin/Debug/net8.0-windows/Hgvd.Tests.exe
```

★ **界面回归必须在发行版上做**：`EpisodeRow` 的属性通知测试针对的是 Avalonia 的
`EpisodeRow`（`hgvd-csharp/src/Hgvd.Tests/AvaloniaEpisodeRowTests.cs`）。
踩过的坑是「改了值但界面不刷新」—— 绑定的是**计算属性**（`SizeText` / `SpeedText`），
setter 只通知自己就不会触发重新求值。这类 bug **必须断言通知事件的名字**，
只断言最终值测不出来（值本身是对的）。

## 四、GitHub Actions

| 工作流 | 触发条件 | 做什么 |
|---|---|---|
| `.github/workflows/ci.yml` | push / PR 到 `main` | C# + Python 离线回归，并验证能 publish 出单文件 exe |
| `.github/workflows/release.yml` | 推 `v*` 标签 | 离线回归 → 按标签版本 publish → 核对产物版本 → 创建 Release 并上传 exe |

CI 用专用的 `.github/nuget.ci.config`（只走 nuget.org）——
仓库里 `hgvd-avalonia/NuGet.config` 把 `nuget.azure.cn` 排在第一位（国内快），
但托管 runner 在海外。

★ **CI 上不能跑 `--uitest`**：它需要真实登录态与收藏夹。
★ **Windows runner 的 stdout 是管道**，Python 会取 ANSI 代码页（cp1252），
打印中文会 `UnicodeEncodeError` ⇒ 工作流里设了 `PYTHONUTF8=1`，
`tests/run.py` / `hgvd/cli.py` 也会把 stdout 重配为 UTF-8。

## 五、发版

### ★★ 「发新版」标准流程（用户 2026-11-21 定义）

「发新版」这一个指令 = 下面四件事，按顺序做完：

| 步 | 做什么 | 命令 |
|---|---|---|
| 1 | **按规则升版本号** | `python tools/bump_version.py x.y.z` |
| 2 | 同步文案（README / release.yml 的本版更新 / docs 里的示例名） | 手工 |
| 3 | **发本地目录版**（`pkg/`，**本地不再发 zip 与单文件版**） | `cd hgvd-avalonia && ./build.cmd verify` |
| 4 | **推送远程仓库 + 触发 Release** | `bash tools/publish_release.sh vX.Y.Z` |

> ★ **版本位规则**：功能性变化（新增 / 裁掉能力、下载口径变化）→ **minor**；
> 纯缺陷修复 → **patch**。
>
> ★★ **「本地不发 zip / 单文件」只约束本地**：`build.cmd` / `build.sh` 只产
> `pkg/hgvd-downloader-vX.Y.Z/`。**GitHub Release 的产物形态不变** —— CI 的
> `release.yml` 仍照旧产出 `zip` + 单文件 exe 并上传（那是给公众下载的）。

### 只发标签（已经构建验证过）

```bash
bash tools/publish_release.sh v1.6.0
```

脚本会：过版本门禁与三道构建门禁 → 同步 `main` → 打带注释的标签 →
推 `main` 与标签 → Release 工作流被触发。
手工等价写法：

```bash
git tag -a v1.6.0 -m "发布 v1.6.0"
git push origin main v1.6.0
```

★ **标签版本号 = 产物版本号 = 界面显示的版本号**（单一来源）。
工作流会核对 exe 的 `FileVersion` 与标签是否一致，不一致直接失败。

> ★★ **推送 / 发布必须与版本号同步（已固化成门禁）**
>
> 版本号有三处副本：`build.cmd` 的 `VER`、`build.sh` 的 `VER`、csproj 的 `PkgVersion`。
> 只改一处就发版，会出现「exe 名是新版、界面显示旧版」或「同一标签两次构建产物不同」。
>
> ```bash
> python tools/bump_version.py 1.4.1   # 三处一起改（保留 build.cmd 的 CRLF）
> python tools/check_version.py        # 只查一致性
> git add -A && git commit -m "chore: v1.4.1"
> bash tools/publish_release.sh v1.4.1
> ```
>
> `publish_release.sh` 与 `release.yml` 都会跑 `tools/check_version.py <tag>`：
> **标签与仓库版本不一致就拒绝**，不会产出同名不同物的包。
>
> 手工 `git push origin vX.Y.Z` 也拦得住：仓库带 `.githooks/pre-push`，
> 每个 clone 做一次 `git config core.hooksPath .githooks` 即可（推分支不拦，只拦标签）。
>
> 历史：`v1.3.0` 指向合并前的 `6cbe4c2`（只有红果），所以合并兴趣岛后用了 **v1.4.0**。

发布物：<https://github.com/chisenin/hgvd-downloader/releases>

## 六、命名约定

- 成品 exe 统一叫 **`hgvd-downloader-vX.Y.Z.exe`**。
- 版本号唯一来源 = `build.cmd` / `build.sh` 里的 `VER`
  （等价于 csproj 的 `PkgVersion`）。
- 目录前缀统一 `hgvd-`。

## 七、版本号需要同步的位置

改版本时逐处核对（少一处就会出现「exe 名对、界面显示旧」）：

| 位置 | 用途 |
|---|---|
| `tools/bump_version.py` | ★ **唯一推荐入口**：一次改下面三处，保留 build.cmd 的 CRLF |
| `hgvd-avalonia/build.cmd` / `build.sh` 的 `VER` | 本地构建默认版本 |
| `hgvd-avalonia/src/Hgvd.Avalonia/Hgvd.Avalonia.csproj` 的 `PkgVersion` | 兜底默认值；决定程序集名与 `FileVersion` |
| `tools/check_version.py` | ★ 门禁：三处一致 + 标签一致；`publish_release.sh` / `release.yml` 都会调 |
| 界面「关于」/ 底栏 | 读 `Assembly.GetName().Version`，不写死 |
| `.github/workflows/release.yml` | 按 tag 传 `-p:PkgVersion=`，并核对 `FileVersion` 前缀 |
| `docs/` 与 `README.md` 里的示例名 | 仅文案，跟着改（历史版本叙述别改） |

★ **不要在 XAML 里写死版本**：`MainWindow.axaml` 的 `Title` / `LblVersion`
里的初值只是设计器占位，运行时会被代码覆盖（以程序集版本为准）。
若发现界面显示旧版本，先查是不是漏了 `LblVersion.Text = ...` 那一行。
