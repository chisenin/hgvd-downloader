## 一、协议层

### 1.0 ★★★ 空 body 的四次误判（改代码前先读这条）

这个项目历史上**四次**把「拿不到数据」判成了错误的根因，每次都白烧几十分钟：

| 时间 | 当时的结论 | 实际根因 |
|---|---|---|
| 11-13 上午 | 单账号单 IP 频率上限很低 | **用错签名函数**：带 `x-medusa` 打播放接口，服务端直接丢 |
| 11-13 晚 | 「账号级风控」，7 轮退避 19 分钟 | C# `x-argus` 移植 bug（`ts<<1` 溢出 / PKCS#7 填充值） |
| 11-14 | 「网关丢 `video_model`」= 服务端节奏限制 | 那个端点后来被**整体停用** |
| 11-20 | 「v04.10 改了 native 签名算法」 | **接口换成了 `preload`，且服务端根本不校验签名** |

⇒ 其中「限流 / 账号风控 / 签名变了」三条都**已被证伪**：真正的限流必然随间隔恢复，
而签名根本没人校验。

★ 最后这次是决定性的：真机自己发的 `X-Argus` / `X-Ladon` 只有 **3 字节**，
宿主机上**去掉全部签名头**重放仍 `code=0`。协议细节与抓包方法见
[`05-抓包与协议排查.md`](05-抓包与协议排查.md)。

**可复用的判据**：

- 真正的限流**必然随间隔恢复**。7 轮退避 19 分钟没恢复、隔几天不打第一发照旧空
  ⇒ 观察不到恢复，就不是限流。
- **先抓「对方的真实样本」，再谈算法。** 这次一次抓包就推翻了几个小时的反向推理。
- 「拿到 JSON」只能证明**这个端点不验签**，不能证明签名有效
  （`album_detail` / `multi_video_detail` 完全匿名也返回 `code=0`）。
- **零字节 body 先怀疑「路径/端点变了」**，而不是「签名算错了」。
- 报错要**如实分类**：空 body / 502 / 非 JSON / 网络错是四件事，
  一律报成「限流」会把排查带偏（代码里 `ApiFailure` 枚举守住这条）。

**历史证伪实验（旧端点上的，探针仍保留）**：

```bash
python -m tools.rate_probe 7662736695145548824 --vtype 0 -n 30 --gap 0      # 频率维度
python -m tools.emptybody_probe 7709143946680601624 --vid 7662736695145548824  # 范围维度
```

当时的观测：第一发就空、**匿名/不存在的 vid/拆掉 argus+ladon 全空**、
`v1`/`v2` 都空、同刻免签名 `bookshelf` 返回 243 项、匿名 `album_detail` 57 KB ——
这些只能说明「**该端点对任何请求都回空**」，不能说明原因；
真正的原因（端点被替换）是后来抓包才确认的。

### 1.1 「HTTP 200 + 空 body」是症状，不是根因

至少有四种成因，**必须分开报**：

| 现象 | 含义 | 处理 |
|---|---|---|
| JSON `code=0` 且有 `video_list` | 成功 | — |
| `code=101000` | **内容类型 key 用错**（教学 1000/1001、视频流 1004） | 换 key，别重试同一个 |
| `code=100001` | 参数错（典型：body 缺 `biz_param`） | 补 body 字段 |
| 返回 **零字节 body** | 端点已停用 / 网关丢弃（**不是限流**，见 1.0） | 先怀疑路径变了 |
| 返回 **502 / 404 且非 JSON** | 端点路径或网关已变更 | 核对路径 |

⇒ **绝不要**把空 body 笼统写成「服务端限流」。
⇒ 排查时**先证伪再下结论**：换一个 host、换一个端点、对同一集发两发，
把「客户端实现问题」和「服务端状态问题」分开。

### 1.2 「换 host」是最便宜的一步鉴别

同一个接口换网关就通，说明问题根本不在客户端。
空 body 时**立刻换网关**（秒级），**不要退避等待**（分钟级）。

★ 配套：故障转移分支要**能测**。用 `HGVD_PLAYBACK_HOST` 把必定丢请求的网关
放第一位，就能验证「空 body → 立刻换下一个」真的被执行过 ——
否则这条代码路径可能从没跑过就交付了。

### 1.3 业务错误码不该退避重试

`code=101000` 是参数错，重试一万次也一样。退避只留给真正的网络故障。

### 1.4 批量下载遇到空 body 别空转

播放接口被丢弃时，旧实现会一直退避重试，整批能空转几十分钟。
现在：**连续 2 次空 body 就熔断**，立刻停下并提示改用「提取 App 缓存」。

### 1.5 细节

- 网页版详情页路径是 `/detail?series_id=<id>`（不是 `/series/<id>`），
  正则要**非贪婪**。
- 播放 body 是 **gzip 后的 JSON**：`Content-Type: application/json` 与
  `Content-Encoding: gzip` 两个头都要有，body 也要真的压过。
- `video_model` / `video_list` 都可能是**嵌套 JSON 字符串**，解析前先判类型。
- 备用直链 `backup_url` 解析了但下载器没用过它 —— 主链可用就没必要。
- 收藏接口「不带 cookie」和「带假 cookie」返回不同：不带 cookie 返回空列表，
  别误判成「接口挂了」。

## 二、签名链

### 2.1 移植密码学的两个隐形杀手

- **C# 的 `int` 溢出**：`int` 是 32 位有符号，`ts << 1` 在时间戳较大时直接溢出成负数
  ⇒ 签名与预期完全无关。Python 无此问题 ⇒ **「Python 通、C# 不通」时优先查溢出**。
- **PKCS#7 填充值**：填充字节写错不会报错，但服务端解出来不是合法 JSON
  ⇒ 表现与「被限流」一模一样 —— **这正是三次误判的入口**（§1.0）。

### 2.2 黄金向量必须是真实签名

曾经 `golden_headers.json` 里的 `x-argus` 只是 **4 字节时间戳桩**，
真签名从来没被逐字节比对过 ⇒ 移植 bug 长期潜伏，直到真正去比对才暴露。

⇒ 黄金向量必须是真实字节级样本。它守的是**移植正确性**，
**不再**是「能不能下载」的判据（播放链路已不发签名头）。

### 2.3 body 的字节必须完全一致（仅对仍带签名的端点）

`x-gorgon` / `x-ss-stub` 都覆盖 body ⇒ 字段顺序、空格、编码都要一样。

## 三、界面层（Avalonia）

### 3.1 容器型子控件别用 Left/Right 对齐

> `Border` 没有子内容 ⇒ `DesiredSize` 恒为 `(0,0)`。
> 填充层设了 `HorizontalAlignment = Left` 且从未被 Measure ⇒
> 排版时宽度被收缩到 `DesiredSize.Width` = **0**
> ⇒ **整块渐变填充被压成 0 宽**，界面上只剩一条空轨道，
> 看起来像"渐变没实现"。

★ **要么显式 Measure，要么用 `Stretch`。**

### 3.2 「界面效果没出来」时先证明它画出来没有

抓窗口像素、沿控件中线输出颜色分段，比看代码可靠得多：

- 渐变存在 ⇒ 能看到连续的颜色过渡（`#9FDFBD → #43B075`）
- 渐变不存在 ⇒ 整条只有一个颜色（轨道色 `#E4EAF3`）

只贴代码容易把方向判错（以为「渐变定义写错了」或「绑定没生效」），
而真实原因可能是**排版把宽度算成了 0**。

### 3.3 「改了值但界面不刷新」

绑定的是**计算属性**（`SizeText` / `SpeedText` / `Percent`）时，
setter 只 `Raise(nameof(自己))` 是不够的 —— **依赖属性必须一起通知**。

⇒ 这类 bug **必须断言通知事件的名字**，只断言最终值测不出来
（值本身是对的，只是界面没刷新）。

### 3.4 右栏是「下载清单」，不是「当前剧的分集」

2026-11-17 用户反馈调整：**收藏夹默认全选**在几十上百项时不现实，
而且「点一行 / 点勾选框 → 右栏整表替换成这一部」会把已经看好的分集冲掉。

现在的语义：

| 动作 | 结果 |
|---|---|
| 进场 / 刷新收藏夹 | 一个都不勾，右栏清单为空 |
| 勾选剧目 A | A 的整组分集**追加**到清单尾部（带「A · 共 N 集」分组标题行） |
| 再勾剧目 B | B 的整组**继续追加**，A 原样保留 |
| 取消勾选 A | 只把 A 那一组移除，B 不受影响 |
| 点列表行 | **什么也不做**（仅高亮后立刻清空，避免误以为「点行=要下载」） |
| 点「下载」 | 有选中行只下选中；否则下清单里所有「待下载」的 |

★ 多部剧同处一个清单时，**集号必须各归各的**：
每行带着自己的 `SeriesId` / `SeriesTitle`，下载时按 `vid → Episode` 缓存取原始数据，
文件名仍是「剧名.集号.标题.mp4」，不会出现 A 的第 5 集和 B 的第 5 集同名。

★ 为什么**红果侧**不设「全选」和「批量下载 (N)」入口：
全选会让 236 部剧一次性触发 236 次 `album_detail` 请求；而「勾选即入清单」之后，
批量下载已经等价于「勾多部 → 点下载」，留着两个入口只会让人猜哪个才算数。
（兴趣岛侧保留「全选」：营的数量少，且用户常整营归档，代价可接受。）

### 3.5 其它 Avalonia 坑

- `ToolTip` 是附加属性 → `ToolTip.Tip="..."`，写成属性直接编译失败。
- Avalonia 没有 `DataTrigger` → 换成 VM 上直接暴露 `bool` / `IBrush`。
- `<Window>` 只能有**一个**根子元素 → 否则 `AVLN3000: Content 无法多次赋值`。
- 没有内置 `MessageBox` → 自写 `MsgBox`。
- `Application` 上没有 `MainWindow` / `Shutdown` → 在
  `IClassicDesktopStyleApplicationLifetime` 上。
- `Application.TryFindResource` 不存在 → `Application.Current.Resources.TryGetValue`。
- 后台线程不能调 `Window.Show()` → 用 `Dispatcher.UIThread.Post`。
- 自绘窗口（`SystemDecorations="None"`）要自己做缩放热区。
- 窗口在运行时创建 → App 级资源用 `DynamicResource`，`StaticResource` 可能找不到。

### 3.6 ★ 发布裁剪（PublishTrimmed）的三条硬约束

`PublishTrimmed=true` + `TrimMode=partial` 能把自包含产物体积砍掉约一半
（未内置 ffmpeg 时实测 89 MB → 41 MB；当前发行物含内置 ffmpeg：
目录版 77 MB / zip 54 MB / 单文件 58 MB）。省下来的全是没人引用的 BCL 整块
（`System.Data.Common` / `DataContractSerialization` / `VisualBasic.Core` …）。
但有三条必须守住，**任何一条破了都不报错**：

| 约束 | 破了的后果 |
|---|---|
| `Avalonia.*` 全部 `TrimmerRootAssembly` 保根 | `Avalonia.Markup.Xaml` 被裁 53%、`Avalonia.Base` 裁 30% ⇒ **反射绑定静默失效**（本项目 `AvaloniaUseCompiledBindingsByDefault=false`，XAML 全靠反射） |
| `<JsonSerializerIsReflectionEnabledByDefault>true</…>` | `AppConfig.Save()` 抛 `Reflection-based serialization has been disabled for this application`（.NET 8 在 trim 下默认关掉 `System.Text.Json` 反射序列化器） |
| `restore` 带 `-p:Configuration=Release` | `ILLink.Tasks` 是 **restore 阶段**按 `PublishTrimmed` 决定下不下的；restore 默认按 Debug 评估 ⇒ 拉不到 ILLink ⇒ publish **静默不裁剪**（体积翻倍，一个警告都没有） |

自己的两个程序集也必须**整程序集**保根：里面全是反射绑定、`JsonSerializer` 反射序列化、
以及 `MumuAuth` 的 `dynamic` + `Type.GetTypeFromProgID` COM 调用。
保根要写 `$(AssemblyName)`——主程序集的 AssemblyName 是
`hgvd-downloader-v$(PkgVersion)`，写成 `Hgvd.Avalonia`（那是 RootNamespace）会报 `IL1032`。

★ 顺带：`System.Private.Xml` 7.7 MB **裁不掉**，Avalonia 自己依赖它；别在这上面浪费时间。
`libSkiaSharp` 9 MB + `av_libglesv2` 5.2 MB + `HarfBuzzSharp` 1.8 MB 是渲染底价，
删了要么不显示要么中文排版乱。

★ 验收标准不是「能编译」：必须 `--uitest` 全部通过 **并且** 真跑一次端到端下载
（`--batchtest 1`，真下 1 部 1 集约 23 MB）。裁剪的破坏是静默的——
编译、启动、开窗、读收藏夹全都正常，只有点到某个功能才炸。

### 3.7 ★ 窗口缩小时右侧按钮被挤出（DockPanel 的锅）

2026-11-21 用户截图：窗口拖窄后「提取App缓存」被挤出窗口右边缘。

**根因不是 MinWidth 太小**，而是工具栏用了 `DockPanel`：

```xml
<DockPanel LastChildFill="False">
  <StackPanel DockPanel.Dock="Left">…跑马灯 + 筛选…</StackPanel>
  <StackPanel DockPanel.Dock="Right">…画质 + 下载/暂停 + 提取缓存 + 历史…</StackPanel>
</DockPanel>
```

DockPanel 是「按子元素顺序依次 dock，后面的拿剩下的」——左组先占满，
右组拿到的是剩余宽度，不够就**被裁**（不会反过来让左组缩）。

★ 正解：`Grid ColumnDefinitions="Auto,*,Auto"` —— 两侧 `Auto` 按内容排布、
绝不压缩，可压缩的只有中间那段空白。

★ MinWidth 不能拍脑袋，要实测：`--uitest` 第 ⑪ 条从 900 开始逐级加宽，
找出「四个按钮都在框内」的最小窗口宽（**实测 980**，设 `MinWidth=1020` 留余量）。
探测时**必须把 `MinWidth` 临时清 0** —— 否则 `Width=900` 会被 MinWidth 顶回去，
第一轮就「通过」，探测形同虚设（踩过一次）。

★ `tools/shot_app.py` 支持 `--w=` / `--h=` 指定窗口尺寸，可截图人工复核。
注意 Avalonia 不响应外部 `SetWindowPos` 的尺寸（会用自身 Width/Height 覆写），
要么改 XAML 初始尺寸，要么让程序自己设 `Width`。

### 3.8 双击清单某一集 = 单独下载这一集（2026-11-21 加）

`LstEpisodes.DoubleTapped` → `EpisodeRowFromEvent()` 回溯到 `ListBoxItem`
→ `DownloadOneAsync(row)`。命中测试要往上找 `ListBoxItem`：
用户点的往往是行内的 `TextBlock`，`e.Source` 不是 `ListBoxItem` 本身。

★ 与点「下载」的语义区别（改这块前先想清楚）：

| 入口 | 语义 | 短剧过滤 |
|---|---|---|
| 「下载」按钮 | 批量：有选中行下选中的，没选中下所有待下载 | 有（历史遗留，见下） |
| **双击某一行** | **明确指定这一集**，不看勾选、不受筛选影响 | **无** |

双击不过滤短剧是故意的：用户已经点到具体某一集了，再替他把短剧剔掉只会让人困惑。
（注：「下载」按钮那个短剧过滤是 2026-11-20 之前留下的 —— 当时短剧解不出画面；
DRM 切片修好之后短剧已经能正常下载，这个过滤其实该去掉了，见 §5.5。）

★ 并发保护：`DownloadOneAsync` 开头的 `if (_downloading)` 拦住"下载中再双击"，
回一条日志而不是静默丢弃。

★ 回归：`--uitest` 的 ⑦★ 组（5 条）直接调 `DownloadOneAsync` 并断言
「钩子只被调用 1 次」「下载的正是那一行」「其它行没被顺带重下」。
事件绑定本身由 XAML 编译保证。

## 四、跨平台 / 编码

### 4.1 Windows 控制台编码

Python 在**输出被重定向到管道**时取 ANSI 代码页，而不是终端编码。
非中文代码页（如 CI runner 的 cp1252）上打印中文会
`UnicodeEncodeError` 直接崩掉。

⇒ 脚本启动时把 stdout/stderr 重配成 UTF-8：

```python
for _stream in (sys.stdout, sys.stderr):
    try:
        _stream.reconfigure(encoding="utf-8", errors="replace")
    except (AttributeError, ValueError):
        pass
```

⇒ CI 里再补一层 `env: PYTHONUTF8=1`（PEP 540 UTF-8 模式）。

★ 注意：中文 Windows 控制台是 GBK（能编码中文），
**本地永远复现不出来** ⇒ 只能在 CI 上暴露。

### 4.2 C# 侧

- `WinExe` 程序默认没有控制台 → 要输出就 `AttachConsole(-1)`（挂父进程），
  并设 `Console.OutputEncoding = Encoding.UTF8`。
- 路径是 UTF-8 → 文件/进程操作一律用宽字符 API
  （`CreateFileW` / `MoveFileW` / `_wfopen_s` / `CreateProcessW`），
  否则按 GBK 解释 → 中文路径全失败。
- 源码里的中文不要用 `\xNN` 转义（十六进制转义贪婪，`\x88A` = 0x88A）→
  直接写 UTF-8，编译加 `/utf-8`。

### 4.3 模拟器（MuMu）接入：别写死安装目录

**踩过的坑（2026-11-17，真实故障）**：模拟器开着、安卓机开着、红果 App 已登录，
但「重新授权」始终失败。两个根因：

1. **安装目录写死**。旧代码只找 `…\Netease\MuMu\nx_main\MuMuManager.exe`，
   而本机装在 `D:\Program Files\Netease\MuMuPlayer-12.0\…` ——
   `FindMumu()` 直接抛「找不到 MuMuManager.exe」。
2. **RPC 里的相对路径静默返回空**。`MuMuManager.exe sh -v N -c "cat com.phoenix.read/…"`
   拿到 0 字节，看起来像「App 没登录」，实际是路径没带 `/data/data/`。
   ⇒ 所有 `cat` / `ls` 一律用**绝对路径**。

⇒ 这是**公开发布**的工具，使用者多、安装位置千变万化，**不能把「设环境变量」当正常路径**。
官方安装包一定会留下痕迹，按可靠性排序：

| 顺序 | 来源 | 说明 |
|---|---|---|
| ① | `~/.hgv_tool/mumu_manager.txt` | 上次命中/用户手选的缓存，命中即秒开 |
| ② | **运行中的 MuMu 进程** | `MuMuNxMain` / `MuMuNxDevice` / `MuMuPlayer` 的 `MainModule.FileName`；授权时模拟器必然开着，最权威 |
| ③ | **开始菜单 / 桌面快捷方式** | 安装包必建 `.lnk`（本机实测直接指向 `…\nx_main\MuMuNxMain.exe`），装在任意目录都能命中；用 `WScript.Shell` 解析 TargetPath |
| ④ | 卸载注册表 `DisplayName` 含 `MuMu` | `InstallLocation` / `DisplayIcon`（去掉尾部 `,0`）/ `UninstallString` |
| ⑤ | 各盘 `Program Files`、`Netease`、盘根 | 枚举名字含 `MuMu`/`Nemu` 的目录 |
| ⑥ | `PATH` | 兜底 |
| ⑦ | 环境变量 `HGVD_MUMU_MANAGER` | 只留给售后/高级用户，不写进用户可见的提示 |

每个候选都做「**向上回溯 N 层 + 拼相对位置**」，兼容这些布局：
`nx_main\MuMuManager.exe`（MuMu 6 / MuMu Player 12）、`shell\MuMuManager.exe`、
`nx_device\shell\MuMuManager.exe`、根目录直放。

**兜底交互**：GUI 的「获取授权」（旧文案叫「重新授权」）在找不到模拟器时会直接弹**文件选择框**，
让用户选一次 `MuMuManager.exe`（选完写进缓存，下次不用再选）。
Python 版沿用同一缓存文件，所以 GUI 里选过一次，命令行也认。

另外：实例要 **0~7 全探**，不能「0/1 没启动就收工」—— 用户可能只开了实例 2。

★ 回归：`MumuLocateTests`（C# 7 项）用临时目录模拟任意安装根目录、
并用真实 `.lnk` 验证快捷方式解析，锁住「不依赖具体目录名」；
总计离线回归为 **C# 72 项 / Python 87 项**。
诊断入口 `hgvd-downloader-vX.exe --authcheck` 会打印实际找到的 MuMuManager 路径、
**每台实例的授权状态（✓有效 / ⚠无法验证 / ✗失效）与 uid、最近活动时间、install_id**，
以及最终选中哪一台。

### 4.4 多开 / 多台安卓机：怎么拿到「正确那台」的授权

MuMu 多开时每台实例都是一个独立安卓系统，可能各自装了红果、各自登录过。
**只按「最近修改时间」猜会挑错**，评判标准必须是服务端认不认这份 cookie：

1. `CollectCandidates` 逐台读 `cookieStore` + 设备身份，记下最近活动时间；
2. 用 `passport/account/info/v2/` 在线验证（有效时顺带拿到 `uid` / 昵称）；
3. 按最近活动倒序，**取第一台「服务端认可」的**；全部网络不通时退回最近活动那台并标注
   `⚠ 无法在线验证`（不把用户挡在门外，也不误杀本来有效的授权）；
4. 显式 `--index N` 时不验证，直接读指定实例。

**「同一账号在多台实例里授权互斥」的正确解释**：不是账号互斥，而是两种技术性假象 ——

| 假象 | 机理 | 工具怎么消除 |
|---|---|---|
| 设备身份串台 | 多开常是复制镜像 ⇒ 几台 `sessionid` 相同但 `install_id` / `device_id` 不同；拿 A 的 cookie 配 B 的设备签名，服务端直接拒（HTTP 200 + 空 body，很像「没授权」） | `device.json` 按 `install_id` 归档到 `devices.json`；`Device` 取值时用 **cookie 里的 install_id** 取同源档案 |
| 旧 session 被顶 | 两台各自独立登录同一账号，后登的会把先登的 session 顶掉，先登那台就「失效了」 | 逐台在线验证，自动挑还活着的那台；`--list-mumu` 会显示哪台 ✗ |

**引导式等待（分散安装位置 + 忘记先开模拟器时的正解）**：
找不到授权不直接报错，而是提示「打开装了红果的安卓机 → 打开红果 → 确认已登录」，
并**每 2 秒扫一次运行中的实例**，读到可用登录态就自动继续：

- GUI：`WaitAuthWindow`（置顶小窗，列出各实例启动状态，最多等 180 秒）；
- CLI：`python -m hgvd login --watch [--watch-timeout 180]`。

★ 回归：`DeviceStoreTests`（C# 3 项）锁住「A/B 两台设备档案互不覆盖、未知 iid 回落 latest」，
Python 侧 `B7/B8/B9` 三条对应用例。

## 五、下载器

### 5.1 文件名

- 剧名出现两遍（`《标题》` 前缀 + 独立剧名列）→ 清洗时去重。
- Windows 保留名（`CON` / `NUL` / …）→ 自动加前缀。
- 临时文件用 `*.mp4.part`，成功后才改名 —— 半截文件不会被当成成品。

### 5.2 进度

进度百分比用**整数除法**截断（`down * 100 / total`），
显示的是已下载字节的占比，不是估算时长占比。

### 5.3 默认值改了不生效

「改了默认值，用户却还是看到旧值」—— 通常是**只在 UI 层改了默认值，
没改配置文件里的持久化值**（旧配置优先级更高）。
⇒ 改默认值要同时改「新建配置时的初始值」和「读到旧值时的回落逻辑」。

### 5.4 ★★ 下载目录不可用时**必须失败**，绝不能静默回退

2026-11-20 实测的 bug：`config.json` 里 `OutDir` 配的是 `Z:\movies\hgvd\`，
盘拔掉之后：

- `Config.ResolveOutDir()` 里 `catch { }` 吞掉异常 → 回落到系统「下载」
- 文件被下到 `C:\Users\xxx\Downloads\剧名\…`
- 界面和 `--batchtest` 全都报**「成功 1 集 · 失败 0 集」**

用户既找不到文件，也不知道出了问题。这类"帮用户做决定"的静默回落，
比直接报错恶劣得多。

**现在的约束**（改这块前先看）：

| 层 | 行为 |
|---|---|
| `Config.TryResolveOutDir(out dir, out error)` | 配置了但不可用 → 返回 `false` + 明确错误文本；**不吞** |
| `HongguoService.BuildOutPath()` | 不可用 → 抛 `IOException`（这一集明确失败） |
| `MainWindow.DownloadRowsAsync()` | 开下前先检查一次 → 一次性把整批标失败 + 弹横幅，不刷屏 |
| `MainWindow` 构造 + `StartupAsync` | 文本框显示**用户配置的原值**（不是回落值），启动时弹横幅 |

★ 判据：**凡是"目录/磁盘/权限"这类外部状态，宁可失败也不要替用户换地方。**
★ 回归方式：把 `OutDir` 指向一个不存在的盘符，跑 `--batchtest 1`，
必须得到 `=== ok=0 fail=1 ===` 且错误里带盘符。

### 5.5 ★★ CENC 密钥解包的切片长度（「短剧下不了」的元凶）

`Drm.DeriveContentKey`（C#）与 `hgvd/drm.py` 的 `derive_content_key`（Python）
是同一套算法，但两边切片写法不同，**极易差一**：

```python
# Python：长度 = key_len - 1
hex_key = bytes(buf[1:key_len])
```

```csharp
// C#（2026-11-21 之前错的那版）：长度 = keyLen（多 1）
string hexKey = Encoding.Latin1.GetString(buf, 1, keyLen);
```

后果链条：16 字节 AES key 被取成 **33 个字符（奇数）** →
紧接着 `if (hexKey.Length % 2 != 0) return ""` 判失败 →
`ContentKey` 恒为空 → 加密内容下载后**不解密** →
成品是加密流，`ffprobe` 读不出 `format.duration` →
报「成品无法解析（可能损坏）」。

为什么藏了这么久：**教学类 `encrypt=false`、`spade_a` 为空，根本不走这条路径**
⇒ 只有短剧（和少数加密内容）会坏，而短剧本来就"不建议下载"，测得少。

★ 护栏：`DrmTests`（6 项）用真实黄金向量断言 `spade_a → 32 个 hex 字符`。
切片错位时长度立刻变 33，测试直接失败。
★ 判据：短剧 `codec=bytevc1` 且 `encrypt=True`；解密后 ffprobe 应报 `hevc / hvc1`。
★ 另一个同源小坑：JSON 的 `true` 经 `J.Str` 会变成 `"True"`（`bool.ToString()`），
  判断 `encrypt` 时要同时认 `"true"` / `"True"` / `"1"`，只写小写会恒判成未加密。

### 6.1 ★★ 发版门禁：`build.sh verify` / `build.cmd verify`

IL 裁剪（§3.6）的破坏是**静默**的，而 GitHub Actions 跑不了界面自检和真下载
（要真实登录态与收藏夹）。所以这两步只能卡在本地：

```bash
cd hgvd-avalonia && ./build.sh verify      # 或 build.cmd verify
```

它做三件事：构建 → `--uitest`（全部通过）→ `--batchtest 1`（真下 1 部、最多 2 集）。

★ 判据是解析 `%USERPROFILE%\.hgv_tool\uitest.log` 与 `batchtest.log`
—— 这两个开关**恒返回 0**（WinExe），靠退出码判断等于没判断。
脚本会先删旧日志再跑，防止拿上一次的结果冒充通过。

`tools/publish_release.sh` 会检查这两份日志是否在 **24 小时内**且通过，
不过就拒绝打标签（`uitest.log` 要有 `=== fail=0 ===`；
`batchtest.log` 要有 `=== ok=N` 且 N≠0）。绕过只能显式
`HGVD_SKIP_VERIFY=1`。
