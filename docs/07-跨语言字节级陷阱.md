# 跨语言 / 跨库的字节级陷阱（写实现前先读）

> 目的：把「Python 能跑、换 C# 就静默失败」这类问题**在写代码之前**拦住。
> 本文件只记**库行为差异**与**已验证的坑**，不复述算法原理。

---

## 0. 核心原则（这次用血换来的）

1. **不要假设两个库的序列化结果字节相同**，哪怕它们都「符合标准」。
   标准通常只规定「可以是什么样」，不规定「末尾有没有换行」这种细节。
2. **拼接结构化文本（PEM / JSON / header）时，边界字符必须自己显式写死**。
   不要依赖某个库的 `xxx_bytes()` 恰好带/不带分隔符。
3. **验证要在最小闭环里做**：先让两个语言的实现**对着同一个权威工具**（`openssl`、
   黄金向量文件）跑，再去碰真实设备。这次定位花了几小时，就是因为一开始在设备上试。
4. **同一个 bug 换语言还会再犯**。C++ 不会自动比 C# 更接近 Python ——
   Python 的安全性来自「大整数 + bytes 不可变切片 + 库恰好带换行」，不是「接近底层」。

---

## 1. PEM 拼接：两个证书之间必须有换行

### 症状（2026-11-21 实测）

C# MITM 代理握手时，App 全部报 `AuthenticationException`；
内层是 `Win32Exception: 处理证书时出现未知错误`。同一份 CA 在 Python 侧一切正常。

### 根因

`X509Certificate2.ExportCertificatePem()` 返回的字符串**末尾不带换行**。
照抄 Python 的 `cert_pem + ca_pem` 写法直接拼，得到：

```
-----END CERTIFICATE----------BEGIN CERTIFICATE-----
              ↑ 两个标签粘在一行
```

结果：`.NET` 无法解析整链 → **静默降级成只加载叶证书** → 客户端只收到一张自签叶证书，
构建不到信任锚 → 拒绝。握手失败发生在服务端加载证书时，与 App、网络都无关。

### 验证方法（本地、不碰设备）

```bash
# 起探针
Hgvd.Tests.exe --tlsprobe 18443 60

# 另一个终端
openssl s_client -connect 127.0.0.1:18443 -servername localhost \
  -CAfile ~/.hgv_tool/ca/ca.crt -brief </dev/null
```

| 状态 | 输出 |
|---|---|
| **坏** | `depth=0 CN=localhost` + `verify error:num=20:unable to get local issuer certificate` |
| **好** | `Verification: OK` |

★ `depth=0` 就是「服务端只发了叶证书」的指纹，看到它立刻去查链拼接，别去查 App。

### 正确写法

```csharp
// ★ 显式 TrimEnd + 显式 "\n"，不要依赖任何库自带换行
string chainPem = leafPem.TrimEnd('\r', '\n') + "\n"
                + File.ReadAllText(CaCertPath).TrimStart('\r', '\n');
var leaf = X509Certificate2.CreateFromPemFile(chainFile, keyFile);  // chainFile 含两行 PEM
```

Python 侧之所以一直正常，是因为
`cert.public_bytes(serialization.Encoding.PEM)` 返回的内容**自带末尾换行** —— 纯属库的巧合。

### 权威依据

- **RFC 7468 §3**：PEM 文件可含多个 textual encoding 实例；ABNF 中
  `posteb` 之后是 `*WSP [eol]`，而 `preeb` 之前可以有 `*eolWSP`。
  规范明确警告：*"Implementers need to be aware that extant parsers diverge
  considerably on the handling of whitespace."*
  <https://rfc-editor.org/rfc/rfc7468>
- **微软官方示例**拼接多证书链时显式 ` $pemBlocks -join "`n" `：
  <https://learn.microsoft.com/zh-cn/entra/global-secure-access/scripts/powershell-active-directory-certificate-service>
- **.NET API 文档**对 `ExportCertificatePem()` 只说「按 RFC 7468 strict 编码」，
  **没有承诺末尾换行** —— 这正是坑的来源：
  <https://learn.microsoft.com/zh-cn/dotnet/api/system.security.cryptography.x509certificates.x509certificate2.exportcertificatepem>
- **pyca/cryptography FAQ** 对 PEM 的要求：单行 header、单行 footer、
  除最后一行外每行恰好 64 字符。它没说末尾换行，但实现里带了：
  <https://cryptography.io/en/3.0/faq>

### 修复后在真实 App 上的验证（2026-11-21）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `[server-handshake] ok` | 0 | **212** |
| `[upstream-handshake] ok` | 0 | **161** |
| `AuthenticationException: 未知错误` | 44~90 | **0** |
| 残余错误 | — | `IOException: 远程主机强迫关闭连接`（连接复用问题，另一回事） |

★ 这个对照证明：**App 之前打不开收藏页，根因就是链没发出去**，不是 Schannel、不是并发、
不是 App 固定证书。修复后握手全部正常。

### 排查中走过的弯路（别再走）

1. 怀疑 CA 缺 SKI → 改了 AKI 生成方式（真 bug，但**不是这次握手失败的原因**）
2. 怀疑带私钥的 CA 塞进 additional → 改无私钥副本（无效）
3. 怀疑并发竞争 → 改锁、改缓存（无效）
4. 怀疑 App 缓存了失败状态 → 反复重启 App（无效）
5. **本地 `openssl s_client -brief` 一看 `depth=0` → 立刻定位**（应该第一步就做）

教训：**设备层症状（App 打不开收藏页）离根因隔了 5 层**。
以后遇到 TLS 问题，第一步永远是本地 `openssl s_client`，不要在设备上试参数。

### 护栏

`--tlsprobe` 探针（本地、无需设备）就是为这条坑准备的。
**以后任何证书链改动，先跑它看到 `Verification: OK` 再碰 App。**
探针已支持「读 CONNECT 的 host 逐域名现签 + 并发」，与真实代理行为一致：

```bash
Hgvd.Tests.exe --tlsprobe 18443 100
openssl s_client -proxy 127.0.0.1:18443 \
  -connect api5-normal-sinfonlinea.fqnovel.com:443 \
  -servername api5-normal-sinfonlinea.fqnovel.com \
  -CAfile ~/.hgv_tool/ca/ca.crt -brief </dev/null
# 期望：Verification: OK
```

### 仍未解决（另一个问题）

代理每连接只转发一轮就关，App 复用连接时收到 FIN →
`IOException: 远程主机强迫关闭了一个现有的连接`。
Python 侧用 `Connection: close` 显式告知客户端；C# 侧还没做同样处理。
这不影响证书链的正确性，但会影响抓流稳定性，下次单独修。

## 2. 私钥 PEM 的两种标签（PKCS#1 vs PKCS#8）

| 库 / 方法 | 输出标签 | 说明 |
|---|---|---|
| Python `private_bytes(..., TraditionalOpenSSL, ...)` | `-----BEGIN RSA PRIVATE KEY-----` | PKCS#1 |
| Python `private_bytes(..., PKCS8, ...)` | `-----BEGIN PRIVATE KEY-----` | PKCS#8 |
| .NET `RSA.ExportRSAPrivateKeyPem()` | `-----BEGIN RSA PRIVATE KEY-----` | PKCS#1 |
| .NET `RSA.ExportPkcs8PrivateKeyPem()` | `-----BEGIN PRIVATE KEY-----` | PKCS#8 |

`X509Certificate2.CreateFromPemFile(cert, key)` 两种都认 —— 这一项目前没踩过坑，
但**跨库传私钥文件时必须确认标签**，否则报的错和上一节一样含糊。

## 3. 有符号整数移位溢出

### 已知案例：x-argus 的 `ts << 1`

| 语言 | 行为 |
|---|---|
| Python | int 任意精度，`3400000000 << 1` 正常得到 `6800000000` |
| C# | `int` 是 int32，溢出成 `-894967296`（静默，不抛异常） |
| C++ | 同样溢出，且是有符号溢出 = **未定义行为**，比 C# 更危险 |

服务端收到错签名后的表现：**HTTP 200 + 空 body**，没有任何错误码。
这是最坑的一类：症状像限流/网关丢包，实际是本地算错了。

护栏：`ArgusTests.cs` 的字节级黄金向量（由 Python 算出，与 Go 参考实现对齐）。

★ 移植任何含移位/乘法的签名算法时，**第一件事**是找出现有黄金向量；没有就先造。

## 4. 字节切片边界

### 已知案例：CENC 内容密钥多取一字节

Python：`buf[1:key_len]` → 取 `key_len-1` 个字符 → 32 hex → 可用。
C# 曾多取 1 位 → 33 字符奇数 hex → `ContentKey` 恒空 → 加密内容不解密 → 成品无法播。

教学类 `encrypt=false` 不走这条路，所以藏了很久才暴露。

护栏：`DrmTests` 断言解出的 key 必须是 32 hex。

★ 凡是 `slice(a, b)` 转 `Substring(a, b-a)` 的地方，**都要单独测边界**。

## 5. 伪 JSON（单引号）不是 JSON

红果的 `video_meta` / `encrypt_info` 字段在部分响应里是
`"{'definition': '360p', ...}"` —— Python 用 `ast.literal_eval` 能解，`json.loads` 不行。

C# 侧加 `J.ObjectOrString` 容忍两种形态；**不要假设服务端返回的一定是合法 JSON**。

## 6. 快速排查顺序（以后别再跳步）

遇到「A 语言通、B 语言不通」：

1. **最小闭环对照**：把 B  language 的输出喂给权威工具（`openssl` / 黄金向量 / hex dump），
   **先看字节，再看业务**。这次少一个换行符，在设备层表现为「App 打不开收藏页」，
   在本地层表现为 `depth=0`，一眼就能定位。
2. **打印内层异常**：TLS 的外层永远是 `Authentication failed, see inner exception`，
   **不打印 `InnerException` 等于没打日志**。
3. **确认是「服务端起不来」还是「客户端拒绝」**：本地 `openssl s_client` 一连就知道。
4. **不要先换语言/换库**：换实现只会换一种犯错方式。先把字节对齐的手段建好。
