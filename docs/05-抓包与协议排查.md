## 一、现行播放协议（2026-11-20 实测）

### 1.1 一次请求的样子

```
POST /novel/player/multi_video_model/preload/v1?<设备参数 query>
Content-Type: application/json; charset=utf-8
Content-Encoding: gzip
User-Agent: com.phoenix.read/74132 (Linux; U; Android 15; …; tt-ok/3.12.13.20)
Cookie: <登录态，可省略>

body（gzip 后的 JSON，字段顺序无所谓）：
{
  "biz_param": {
    "detail_page_version": 0,
    "device_level": 3,
    "disable_digg_stat": false,
    "disable_video_relate_book": false,
    "need_all_video_definition": true,
    "need_mp4_align": false,
    "use_os_player": false,
    "use_server_dns": false,
    "video_platform": 1024
  },
  "dr_scene": "preload",
  "mixed_video_id_map": { "1004": ["<vid>", "…"] }
}
```

响应（`data` 按 vid 分组，`video_model` 是**嵌套 JSON 字符串**）：

```json
{"code":0,"message":"请求成功",
 "data":{"7704267633255779352":{
   "expire_time":1795206519,"video_height":720,"video_width":1280,
   "video_model":"{\"status\":10,\"video_list\":[{\"main_url\":\"https://…\",\"backup_url\":\"https://…\"}]}"}}}
```

`video_list[].main_url` 就是直链，实测 `Range: bytes=0-1023` 返回 `206` +
`ftyp` 头（真 MP4）。

### 1.2 `mixed_video_id_map` 的键 = 内容类型

| 键 | 适用内容 | 用错的后果 |
|---|---|---|
| `1004` | 视频流（推荐流 / 短剧） | 教学集用它 → `code=101000 服务异常` |
| `1001` / `1000` | 教学合集分集 | 视频流用它 → `code=0` 但 `video_list` 为空 |

⇒ 实现里按 `("1004", "1001", "1000")` 依次试，**取第一个能解析出 `video_list` 的**。
Python 见 `hgvd/api/playback.py` 的 `PRELOAD_MAP_KEYS`；C# 见
`Hgvd.Core/Api/SignedClient.cs` 的 `PreloadMapKeys`。

### 1.3 这个接口**不校验签名头**（有判据）

真机自己发的头：

```
X-Argus: hVgAaw==        ← 3 字节
X-Ladon: AT3DcA==        ← 3 字节
X-Gorgon: 8404d080…      ← 46 hex，这个是真的
```

服务端照回 `code=0`。在宿主机上做的对照实验：

| 变更 | 结果 |
|---|---|
| 原样重放（连旧 `x-gorgon`/`x-khronos` 一起带） | `200 / code=0` / 每视频 5 条直链 |
| **去掉全部签名头**（gorgon/argus/ladon/khronos/medusa/helios/ss-stub） | `200 / code=0` |
| **不带 Cookie（匿名）** | `200 / code=0` |
| query 只留 9 个参数 | `200 / code=0` |
| body 去掉 `biz_param` | `code=100001 参数错误` |

⇒ 只有 **body 形状**是硬要求。签名头、Cookie、完整 query 都不是。

### 1.4 落地位置

| 语言 | 入口 | 说明 |
|---|---|---|
| Python | `hgvd/api/playback.py::fetch_playback` | 内部走 `fetch_preload`，返回结构适配成老的 `data.video_model` |
| C# | `Hgvd.Core/Api/SignedClient.cs::PlaybackAsync` | 先走 `PlaybackPreloadAsync`，拿不到流再回落旧接口 |

实测：Python 单集 11.3 MB（174.8s / h264 640x360 + aac）；
GUI `--demo` 连下 3 集（11.8 / 10.7 / 10.6 MB），ffprobe 正常。

## 二、抓包：下次服务端再变，怎么十分钟拿到真机样本

### 2.1 ★ 最容易卡住的一步：CA 装在哪

Android 15 的运行时信任库是 **Conscrypt APEX**：

```
/apex/com.android.conscrypt/cacerts     ← 真正生效的（145 个，ro loop 挂载）
/system/etc/security/cacerts            ← 写在这里**没用**
```

把自制 CA 塞进去（root + SELinux Permissive 即可）：

```bash
# 1) 合并目录：现有 145 个 + 自己的
cp /proc/<zygote64_pid>/root/apex/com.android.conscrypt/cacerts/* /data/local/tmp/cacerts_new/
cp /system/etc/security/cacerts/<hash>.0 /data/local/tmp/cacerts_new/

# 2) 在 zygote 的 mount namespace 里用 tmpfs 盖掉 APEX 目录
#    （之后 fork 出来的 App 进程都会继承）
nsenter -t <zygote64_pid> -m -- sh -c \
  'mount -t tmpfs tmpfs /apex/com.android.conscrypt/cacerts && \
   cp /data/local/tmp/cacerts_new/* /apex/com.android.conscrypt/cacerts/'

# 3) 杀 App 重启；验证：应该是 146 个
ls /proc/<app_pid>/root/apex/com.android.conscrypt/cacerts | wc -l
```

- `<hash>.0` = `openssl x509 -subject_hash_old -noout ca.crt`
- 证书必须 **PEM**、`644 root:root`
- 叶证书要有 `SAN`、`EKU=serverAuth`、`CA:FALSE`，并把 **CA 一起下发**（整链），
  否则客户端报 `CERTIFICATE_UNKNOWN`
- CA 在 tmpfs 里，**重启即消失**，不留后遗症

### 2.2 设备与网络

```bash
# 代理（宿主机监听；MuMu 是桥接网络，客户机能直连宿主 IP）
python tools/metasec/mitm.py --port 8899

# 设备侧
settings put global http_proxy <宿主IP>:8899
am force-stop com.phoenix.read
am start -n com.phoenix.read/com.dragon.read.pages.splash.SplashActivity
```

没有 adb 也能操作 MuMu：

```bash
"/d/Program Files/Netease/MuMu/nx_main/MuMuManager.exe" sh -v 1 --cmd "<shell 命令>"
# ★ MSYS 会把带冒号的参数当路径改写 —— 前面加 MSYS2_ARG_CONV_EXCL='*'
# ★ 取文件：base64 走管道落盘（4.5MB 的 so 实测可行，md5 校验一致）
```

### 2.3 两个工具

| 工具 | 用途 |
|---|---|
| `tools/metasec/mitm.py` | 最小 MITM：自己签叶证书、只宣告 http/1.1、按请求落盘到 `_ref/metasec/bodies/NNNN-*.txt`（含请求/响应体，gzip/chunked 自动解） |
| `tools/metasec/replay.py` | 重放样本：`--restub` 重算 `X-SS-STUB`，`--no-sig` 去掉全部签名头，`--host` 换网关 |

抓一次真机请求 → `replay.py --no-sig` 从宿主机重放 →
**能在主机上复现就说明协议本身没问题**；不能复现就逐项加回参数，差异立刻定位。

## 三、踩过的坑（都别再踩）

### 3.1 判据类：同一个坑踩了四次

| 当时的判断 | 真相 |
|---|---|
| 「服务端限流」 | 用错签名函数 / 移植 bug / 网关丢请求，**没有一次是限流** |
| 「账号级风控」 | 同上 |
| 「网关丢 `video_model`」 | 只是那个端点后来被整体停用 |
| 「v04.10 改了 native 签名算法」 | **接口换了**，签名根本没被校验 |

**可复用的判据**：

- 真正的限流**必然随间隔恢复**。7 轮退避 19 分钟不恢复、隔几天第一发照旧空 ⇒ 不是限流。
- **先抓「对方的真实样本」，再谈算法。** 这次一次抓包就推翻了几个小时的反向推理。
- 「拿到 JSON」只能证明**这个端点不验签**，不能证明签名有效
  （`album_detail` / `multi_video_detail` 完全匿名也返回 `code=0`）。
- 报错要**如实分类**：空 body / 502 / 非 JSON / 网络错是四件事，
  一律报成「限流」会把排查带偏（代码里已有 `ApiFailure` 枚举守住这条）。

### 3.2 环境类

| 坑 | 事实 |
|---|---|
| MuMu 的 adb 端口连不上 | 用 `MuMuManager.exe sh/adb` 走它自己的通道，不需要 adb |
| MuMu 系统盘默认只读 | `setting -v 1 -k system_disk_readonly -val false` 后 `/system` 变 overlayfs(rw)；**但 CA 仍要按 §2.1 放 APEX** |
| 宿主/客户机共享目录 | 宿主 `D:\user\chisenin\docments\MuMu共享文件夹`（配置里就是 `docments`）↔ 客户机 `/sdcard` |
| MSYS 改写带冒号参数 | `MSYS2_ARG_CONV_EXCL='*'`（`LD_LIBRARY_PATH=/a:/b` 会被改成 Windows 路径） |
| 控制台编码 | 本机 GBK，`iconv -f GBK -t UTF-8` 再看；CI 上是 cp1252，用 `PYTHONUTF8=1` |

### 3.3 工具类（做静态分析才会遇到）

| 坑 | 事实 |
|---|---|
| capstone `disasm()` 遇到脏字节**直接停** | 必须 `md.skipdata = True`，否则 2.4MB `.text` 扫到第一处数据就结束，表现为「明明有引用却 xref 全 0」 |
| Unicorn **不允许在 hook 里再 `emu_start`** | 会以 `access violation` 崩；要调库内函数只能 tail_call（LR 指临时 stub、PC 跳过去） |
| `.init_array` 在文件里全是 0 | 目标地址只在 `R_AARCH64_RELATIVE` 重定位表里，必须手动应用 |
| JNI 函数表下标 | 按 **Android jni.h** 真实顺序（215 = RegisterNatives、228 = GetJavaVM），别凭记忆 |
| `pthread_once` 的 init 要真的跑 | 很多全局初始化在里面，返回 0 不算完 |

### 3.4 逆向类（**如果**以后还要碰 `.so`）

- 已 strip，`.dynsym` 只剩 `JNI_OnLoad`；字符串整体加密，静态搜不到 `x-argus`。
- 控制流平坦化 + `svc #0` / `brk #3` 反调试，直接反编译成本极高。
- 注册的 native 入口可能是**诱饵**（跳岛 + 参数重排，直接调只会返回某个入参），
  20 个 `ldr [xN,#0x6b8]` 站点里只有少数是真的。
- 结论：**先证明它值得逆向**，再动手。

## 四、别再试（都已作废，一句话一条）

- 旧端点 `/novel/player/video_model/v1/` —— 已停用，任何请求恒 `200 + 0 字节`。
- 给播放请求造 protobuf body —— 现在是 gzip JSON。
- 改 `x-argus` / `x-ladon` 常量、改 SDK 版本串 —— 服务端不看这些。
- 看到 3 字节的 `X-Argus: hVgAaw==` 就判定「签名错了」—— 那是 App 自己的正常值。
- 用 `MSManager.frameSign`（Java 层）去定位播放签名 —— App 从不调它。
- 用 frida hook 应用来抓请求 —— 抓包（§2）更简单，也不受 arm64 翻译层影响。
